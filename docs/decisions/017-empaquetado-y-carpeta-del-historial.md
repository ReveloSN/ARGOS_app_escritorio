# 017 · Fase 8: motor empaquetado, carpeta del historial e instaladores

- **Estado:** aceptada · 16/10/2026
- **Contexto:** CLAUDE.md §2 y §12 piden el motor como sidecar empaquetado con PyInstaller e instaladores `.msi`, `.deb` y `.AppImage` que funcionen sin internet, con los modelos incluidos. Ajustes debía dejar elegir la carpeta del historial. Con el usuario se acordó: motor en carpeta (onedir) como recurso de Tauri, mover el historial copiándolo y verificándolo, instaladores generados por GitHub Actions al crear una etiqueta de versión y sin firma de código por ahora.
- **Decisión:**
  - **Motor empaquetado (onedir):** `engine/distribution/argus-engine.spec` genera `engine/dist/argus-engine/` con el ejecutable y sus bibliotecas. Se prefirió a un solo archivo (onefile) porque este se descomprime en una carpeta temporal en cada arranque: con spaCy y ONNX Runtime serían varios segundos más cada vez. spaCy, su modelo `es_core_news_md`, ONNX Runtime y los lectores de documentos se incluyen completos porque cargan componentes por nombre. El modelo de embeddings va aparte (ver recursos).
  - **Prueba de humo:** `engine/distribution/smoke_test.py` arranca el binario con datos temporales, revisa los archivos de ejemplo y exige alertas de reglas (identificador), spaCy (nombres) y embeddings (periodo citado). Un instalador con un motor que no arranca no se publica.
  - **Tauri lanza el motor según la compilación:** `EngineLocation` elige `uv run` desde el repositorio en desarrollo y, en las compilaciones de distribución, `recursos/engine/argus-engine` con `ARGUS_MODELS_DIR=recursos/models`. El puerto, el token por ejecución y el cierre por stdin no cambian (ADR 008).
  - **Recursos solo al generar instaladores:** `tauri.bundle.conf.json` añade el motor y los modelos como recursos y se pasa con `--config` al generar instaladores. Así `tauri dev` y `cargo test` no exigen el motor empaquetado ni copian cientos de MB en cada compilación.
  - **Mover el historial:** `POST /preferences/history-folder` ejecuta `ChangeHistoryFolder`: comprueba que la carpeta permita escribir y no tenga ya un historial, copia la base con la copia en caliente de SQLite y las copias de los archivos, verifica sesiones y archivos, y solo entonces guarda la carpeta en `location.json`, que queda siempre en la carpeta de datos del sistema. La carpeta anterior se conserva. Si la elegida desaparece (un disco desconectado), el motor vuelve a la del sistema. Cada problema llega como un motivo (`same_folder`, `folder_not_writable`, `folder_has_history`, `copy_mismatch`) que la interfaz explica en 3 partes.
  - **Reinicio del motor:** tras mover el historial, la interfaz llama al comando `restart_engine` (nuevo token y nuevo puerto) y espera a que el motor responda antes de recargar los ajustes. «Cambiar carpeta» solo aparece en la app de escritorio (puerto `DesktopShell`; en el navegador es `null`).
  - **`ARGUS_DATA_DIR`:** permite usar otra carpeta de datos (pruebas del binario, instalaciones portables) sin tocar la del usuario.
  - **Instaladores en CI:** `.github/workflows/release.yml` corre en Windows (`.msi`) y Ubuntu 22.04 (`.deb` y `.AppImage`; la versión más antigua disponible, para que funcionen en distribuciones con una glibc igual o más nueva). Una etiqueta `vX.Y.Z` publica la versión en GitHub Releases; «Run workflow» los deja solo como artefactos para probarlos.
  - **Sin firma de código:** Windows mostrará SmartScreen al instalar. Firmar requiere un certificado y se deja para más adelante.
- **Dependencias nuevas:** `pyinstaller` (solo desarrollo, para empaquetar), `tauri-plugin-dialog` y `@tauri-apps/plugin-dialog` (selector de carpetas del sistema; permiso `dialog:allow-open`).
- **Consecuencias:** los instaladores pesan varios cientos de MB porque llevan Python, spaCy y los dos modelos; a cambio funcionan sin internet desde la primera ejecución. Compilar la app de escritorio en Windows requiere las Build Tools de Visual Studio (enlazador MSVC); sin ellas, Rust se verifica en CI.
